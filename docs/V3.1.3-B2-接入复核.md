# V3.1.3-B2 收退款接入复核

2026-10-20，B1 完成本地专项验证后作前置复核。B1 云端门禁因 GitHub 登录缺 workflow 权限尚未发起，本文件不代表 B2 已开发或验收。

实施沿用 V3.1.3 设计的 B2 顺序，不把旧免费预约改成收费订单，不使用虚构 SKU 或物流子订单。真实业务的 12 项缺口仍待定。

1. payments 新增明确 SERVICE_TRADE 归属，恰有一个所有者；PaymentService 的 owned、get、lock、attempt、apply、恢复和管理查证全部明确分派。旧商品和会员仍走既有分支，不能落入空 order_id 的商品库存/积分/结算逻辑。
2. 统一时段 → 服务订单 → 支付 → 退款的锁顺序。新旧容量计算还需同时计入 CONFIRMED，不能只计 B1 HELD。收款成功、确认订单、确认名额和收款账本必须同事务；数据库延迟约束验证回执/金额/币种/归属和状态。
3. 只接受模拟测试渠道，两个模拟开关/非生产/暂停守护继续生效；后台恢复与通用支付入口也须遵守，避免从其他入口绕过。消费者请求不能指定 outcome、金额或回执。成功、未知、失败等故障由服务端合成场景或测试夹具控制，页面与报告始终标识模拟。
4. 到期、消费者取消和商家取消先在事务外关闭/查询已发起的渠道尝试，再锁定并复核版本；结果未知继续保留名额与确认责任。确证无收款才能释放。迟到款、重复、错额及错币种进入异常收款与稳定补偿退款号，不能恢复已关闭交易。
5. 已付取消的自动全退须符合冻结的合成条款和履约条件；界线内/开始后/已核销走人工评估。平台评估只形成快照，不发起退款；决定引用未过期且版本相同的评估。拒绝决定保留事实且 refund_id=null。审核权限与二次验证独立登记。
6. 每笔退款有固定请求号、真实已收回执归属、额度占用和租约。成功额与全部在途/未知/耗尽转人工额共同限额；恢复使用原请求号，过期租约只能被新令牌接管，旧令牌不得提交。未知不能显示到账或释放额度。
7. 商品/会员的支付、库存、券、积分和原退款/结算回归不能省略。必测关闭与回款竞争、旧/新业务归属、全额与累计分次退款、租约掉线/重放、审计失败回滚、服务开关关闭后恢复拒绝，以及未授权和生产拒绝。

B2 实际接口、迁移、测试样本及当前契约须另行实现和记录，不能将本清单计入完成数。B3 再接付款后履约、冻结、佣金、结算和三端页面；最终 APK、桌面升级包及快捷入口在全部适用门禁通过后交付。
