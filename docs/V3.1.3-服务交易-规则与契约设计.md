## B 的候选最小模拟范围

一份交易对应一个门店、一项服务、一个完整起止时段、一个名额，CNY 整数分、一次全额预付。洗护/寄养按整个时段计一次，不假定按晚计价；押金/分期、多宠、服务加价、改期、优惠、会员权益和真实支付渠道不在此最小范围。

条款快照必须有可追溯依据、服务与门店、价格、取消界线、佣金、结算缓冲以及版本摘要。规则缺失返回 SERVICE_TERMS_UNAVAILABLE；不得把缺失解释为免费、零佣金或立即可结算。工程案例只使用 TEST_SCENARIO 依据，状态为 ENGINEERING_SCENARIO_ONLY。

消费者先读取可展示的服务条款和服务端报价，再提交 quote_id 与已确认条款摘要 terms_sha256。消费者确认摘要只涵盖实际展示的服务、价格及取消等条款；内部佣金/结算依据另以 policy_snapshot_sha256 冻结，不能把隐藏规则当成消费者已阅读。报价本身不占名额；创建待付款服务订单时在同一事务校验报价有效期、版本、门店/服务/时段状态并预占，预占截止不能晚于时段开始。客户端不能提交应付金额或“付款成功”。价格变更不改写旧交易快照；下单前发现版本失效要求重新报价。

未来所有权扩展采用明确 GOODS_ORDER / MEMBERSHIP_ORDER / SERVICE_TRADE 分派，数据库恰有一个有效所有者；所有支付状态读写、恢复任务和审计都按业务类型分派。新服务交易不引用原零金额预约来规避约束。非生产模拟中若共用时段，容量必须同时计入旧有效预约、新订单预占与已确认名额，并统一锁同一时段。真实环境与模拟环境不得混用容量或财务事实。

## 状态与原子边界

交易、支付、名额、履约、退款、结算分别表达，不把全部状态塞进原 BOOKED/CANCELLED：

| 维度 | 候选状态及关键条件 |
|---|---|
| 交易 | AWAITING_PAYMENT → CONFIRMED / CANCELLED / EXPIRED；CONFIRMED 可经取消受理转 CANCELLED；终态不可自动复活 |
| 支付 | PENDING / PROCESSING / UNKNOWN / SUCCEEDED / CLOSED；UNKNOWN 继续占付款确认责任，不能据本地超时当失败 |
| 名额 | HELD → CONFIRMED / RELEASED；到期先关闭/查证渠道，仍未知不得静默释放后再把迟到款确认履约 |
| 履约 | NOT_STARTED → CHECKED_IN → COMPLETED；NO_SHOW 与 EXCEPTION 由明确规则处理；争议和异常不能自动产生收入资格 |
| 退款 | 每次请求分别保留 RESERVED/PROCESSING/UNKNOWN/SUCCEEDED/FAILED_RETRYABLE/NEEDS_REVIEW；成功和所有在途占用共同限额 |
| 结算 | WAITING_COMPLETION / BUFFERING / FROZEN / ELIGIBLE / PROCESSING / SETTLED / ADJUSTED / NOT_PAYABLE；支付成功不能直接 ELIGIBLE |

付款确认必须验证渠道回执唯一性、金额、币种、支付尝试和订单归属，成功事实与 CONFIRMED/名额转换/账本事件同事务提交。渠道 I/O 在事务外，以稳定指令号、查询恢复、租约与幂等回写处理不确定结果。不同订单的回执不可复用。

消费者在候选取消界线前取消，按测试条款全额退；界线内、开始后、未到店和异常进入人工评估，不自动扣费或退款。商家取消候选为全额退，同样需条款依据。取消被接受可以释放履约责任和名额，但不能显示退款到账；已核销订单不能走简单取消入口。

原取消、核销、退款请求、回调及超时任务须规定统一锁顺序：时段 → 服务交易 → 支付 → 退款/结算轨迹；多条记录按稳定 ID 顺序。并发受理只能产生一个一致结果。版本冲突、幂等重放之前仍校验当前身份和门店权限。未来敏感权限单独登记，不能仅凭 store.nearby.write 操作退款与结算。

关闭或取消后收到迟到款、重复收款、错额或错币种回执，只追加异常收款与补偿退款责任，不恢复交易、不抢回名额、不记可结算收入。未知退款和最终重试耗尽均保留额度占用，转人工恢复前不得重置额度或换退款号。

## 金额与结算不变量

每笔金额使用整数分，所有加减/乘法检查溢出。候选数学口径仅供 B 工程验证：

- 常规确认收款 paid = payable；收款回执唯一、同币种且归属该交易。额外/异常收款单列补偿责任，不混入可结算本金。
- succeeded_refunds + reserved_refunds ≤ paid；UNKNOWN、重试中、NEEDS_REVIEW 均保留 reserved，只有确证未退款并释放责任后才可减少。
- C = half_up(paid × 原快照佣金基点 / 10000)。累计应冲佣金 = half_up(C × min(paid, succeeded_refunds) / paid)，本次冲销仅记累计目标与既记冲销的差；全额退款冲尽 C。
- merchant_net = paid − succeeded_refunds − C + reversed_commission；本轮候选不含渠道费、税费和运费，不能套用真实对账。
- COMPLETED 且缓冲届满、无开放争议/未知收退款/未完成退款、规则快照有效，才可能 ELIGIBLE。NO_SHOW/EXCEPTION/CANCELLED、全额退款不自动进入结算。
- 已结算后的退款追加负向调整，保留原结算批次和原佣金快照；不能改写旧流水，不能把同一余额在商品和服务两处重复发放。真正出款始终由既有正式准入另行控制。

例：测试收款 101 分、佣金 333 bp 得 3 分；先退 34 分累计冲佣 1 分，再退 67 分累计冲佣 3 分，第二次仅新增 2 分。该值是舍入边界测试，不是门店费率。

## 独立契约草案

openapi/design/pawday-v3.1.3-draft.json 独立于当前 pawday-v3.1.2.yaml。servers 使用 design.invalid，所有操作标记 x-runtime-implemented=false；不进入 TS/Dart 当前生成入口，不注册路由、不预置权限、不创建数据库表。

草案覆盖 23 操作：条款草稿/审核和消费者可读条款、服务端报价、订单、模拟付款尝试/状态/查证、消费者与商家取消、退款评估/审核、退款读取、付款后履约及凭证、门店账本及结算预览/执行。评估与结算预览使用幂等 POST 取得快照，不创建退款/出款责任；拒绝退款审核返回审核结果且 refund_id=null，不伪造退款记录。条款审核、退款审核、结算执行要求独立拟议权限和动作绑定二次验证；未创建权限前不得用其他权限兜底。回执、审核结果和可结算余额不由消费者或商家请求直接设定。

所有写操作要求幂等键；修改已有对象需 If-Match；创建以引用快照版本为依据。列表 UUID 游标分页且不超过 100 条。错误区分规则缺失、报价失效、名额冲突、版本冲突、支付确认中、退款占用、结算冻结和未启用。敏感数据仅在归属范围返回，门店列表不暴露消费者用户编号、联系方式或凭证。

设计校验报告明确 evidence_kind=DESIGN_ONLY_SYNTHETIC、runtime_verified=false，不能计作真实 HTTP 或服务交易功能验收。合成案例验证契约结构、金额/状态不变量和当前运行代码隔离。
