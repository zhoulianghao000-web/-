## 下一阶段的执行顺序

1. **M2 收尾（已完成）**：M2.4 PR #2 已复核并合并；M3.1 分支 `codex/pawday-m3.1` 从合并后的主分支创建。不得基于未包含 M2.4 的旧主分支开始 M3。
2. **M3.1 宠物分类与档案**：实现五大父分类、动态物种/品种、版本化年龄阶段规则、宠物档案、过敏/忌口及体重记录；接通 Flutter 宠物页和当前宠物切换。验收归属权限、跨用户访问拒绝、乐观锁冲突与退出清空；年龄或过敏信息未知时保留 UNKNOWN/信息不足，不虚构物种年龄阈值。
3. **M3.2 标准商品与审核**：实现品牌、SPU/SKU、不可覆盖的配料/营养/过敏原与来源版本、商家纠错申请、平台审核及导入校验；商家不得直接修改平台标准配料。
4. **M3.3 商家 Offer**：实现门店报价、上下架及库存 Adjustment 命令，落实 merchant/store scope、服务端 RBAC、唯一约束及审计。
5. **M3.4 确定性适配与搜索闭环**：实现有证据的适配规则，将真实商品/Offer/库存变化接入已有 Outbox 和搜索投影，完成三端业务联调与 M3 验收；过敏冲突不得被广告或排序覆盖，搜索故障不得回滚业务事实。

第一批 **M2 合并收尾 + M3.1** 已完成，交付可运行的宠物档案纵向流程；下一批先评审/合并 PR #3，再从合并后的主分支实施 **M3.2 标准商品与审核**。后续依次推进 M3.2–M3.4；M3 验收通过后进入 M4 购物车、试算、库存预占、订单、模拟支付与结算，AI 解释层按 M5 推进。M3.2 及后续内容为执行安排，不代表已经完成。

## 实施约定

- 默认金额使用整数分，重量使用统一基础单位；订单保留价格、配料版本和优惠快照，不读取当前可变报价回填历史。
- 第三方密钥不进入 App；App 请求统一后端，DeepSeek、支付回调与分账由服务端处理。
- 运营配置使用带版本的数据库配置和审计；系统有启动默认值，但商业参数不能仅写死在客户端。
- 库存锁和支付回调必须在服务端事务/幂等机制下执行；页面按钮禁用不构成并发保证。
- 商家身份、门店认领状态和官方授权分别建模。自营作为特殊商户共享交易系统。
- 演示、沙箱、生产环境清晰区分；模拟支付成功不表示正式支付验收通过。

## 尚待落实的外部条件

正式上线前需要商户和支付主体资料、支付/分账服务商能力、短信与微信应用凭证、DeepSeek 与高德凭证、首发商品数据与授权来源、首发城市及运营政策。它们不阻碍信息架构和本地工程实施，但不能用虚构资料替代生产接入验收。
