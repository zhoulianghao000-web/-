# V2.3 商家 App 与经营分析

范围冻结：2026-10-15。基线为已交付V2.2，消费者身份、单测试账号、11张参考原图及既有业务规则保留。

## 经营分析事实与权限

- PostgreSQL不可覆盖的`merchant_ledger_entries`为统计事实源，不用搜索索引或付款Attempt数推算成交。以账本`created_at`所属上海日历日记账，不伪装为订单创建日/资金到账日。
- 查询起止日包含两端，最多90天，不接受未来日期。响应记录`as_of`，同一只读一致性快照生成总计和完整逐日序列；当天截止该时刻。
- 支付入账=SALE_CREDIT；成功退款=REFUND_DEBIT+SHIPPING_ADJUSTMENT（借方向）；佣金净扣减=COMMISSION_DEBIT-COMMISSION_REVERSAL。收退款净额=支付入账-成功退款；扣佣后经营净额=收退款净额-佣金净扣减。退款按退款记账日回冲，允许单日/期间净额为负。
- 已结算后退款仍计原退款凭证，即使`affects_balance=false`；不再把SETTLEMENT_ADJUSTMENT桥接条目计一次退款。不计SETTLEMENT_DEBIT、MANUAL_ADJUSTMENT及失败/进行中付款退款。入账子订单数按正额SALE_CREDIT的唯一suborder去重（零应付子订单不产生入账，因此不计此指标），退款笔数按退款/运费凭证的唯一refund去重，不乘订单项数。
- 仅整数分CNY；超出JavaScript安全整数范围拒绝响应，避免跨端金额精度丢失。上述金额不是利润、收入确认或可提余额，余额/结算继续走已有账本页面。
- 商家需同时有`ledger.read`和`order.read`；只读所属商户且整张子订单均在员工授权门店范围的事实。无门店订单需现有`order.default-scope`。选择某门店时，仅纳入全部订单项属于该门店的子订单；混店子订单不拆分运费或造分摊，不计入单店分析，界面明确说明。未选择门店时，完整授权的混店子订单只计一次。
- 管理员需`ledger.read`及`order.admin.read`，显式选择商户，可选择该商户门店；消费者、缺权限、跨商戶/门店不得访问。响应不包含消费者手机号、地址、宠物或订单明细。范围撤销后旧请求/客户端不得继续展示过期结果。
- 模拟环境由服务端和构建标识；显示“模拟经营数据”，不得声称真实收入。没有数据时显示零记账事实和空状态，不补造订单。

## 商家App操作范围

独立Flutter工程及Android包`cn.pawday.pawday_merchant`，与消费者包、令牌储存键和设备ID隔离。复用既有商家账号密码登录、refresh、会话撤销、门店RBAC及密码二次验证，不恢复已删除的动态码功能。

首版包含经营分析、授权门店、报价/库存及子订单查看；报价暂停/启用复用版本、幂等及现有敏感动作证明；库存调整使用正式Adjustment命令，不覆盖库存余额。移动端不另造退款或结算规则；售后/履约等完整已有流程按App账号页说明从本机“商家Web工作台”入口在受控本地开发环境继续使用，入口不传递令牌或密码、不绕过登录。后续扩展移动操作须另列范围，不将Web入口称作原生已实现。

App限制请求到配置API及merchant路径；刷新单飞、退出/切账号后旧响应失效，写命令故障重试保持同一个幂等键；版本冲突要求重读后确认，证明不长期保存。Web构建不持久保存令牌；原生安全储存设备会话。模拟版本不允许任意外部工作台链接或真实外部调用。

## 验收与交付

真实PostgreSQL测试统计日界、重复账本约束、退款跨期/结算后冲正、混店范围、权限即时撤销、负净额、空序列、日期与金额边界，并验证新操作的实际HTTP响应契约。商家Flutter验证登录/刷新/退出隔离、RBAC、错误重试/版本冲突、模拟边界和页面布局；Web验证同一经营分析口径。CI增加商家Flutter analyze/test/Web/APK与稳定内部签名门禁。
