# M3.3 商家报价与库存

基线：M3.2 PR #4 已合并，主分支提交 `4d890d48f5170b8c8f33fc167a43e59d624ba622`，本批分支 `codex/pawday-m3.3` 从此创建。

## 报价与范围

商家 `/offers` 页面可选择标准规格、创建草稿报价，修改普通价、可空会员价及履约承诺，明确上架或暂停。标准商品资料不在报价写入字段中；创建和上架要求 SKU、SPU、品牌有效且存在已发布标准资料。会员价不能高于普通价，金额使用整数分。创建不提交库存，初始余额为零。

范围来自当前员工身份及授权门店，不接受 merchant_id/operator。指定门店必须属于商户并在当前员工 scope 内。同商户其他门店也返回 404；列表只包含获授权门店。`store_id=null` 表示商户默认履约范围，需要单独 `offer.default-scope` 权限，门店员工不自动取得该权限。默认范围与各门店报价分别唯一；PostgreSQL 部分唯一索引使用 NULLS NOT DISTINCT，DRAFT/ACTIVE/PAUSED/FROZEN 不能重复。DELISTED 保留历史，允许新建报价。

管理员 `/offers` 页面在 `offer.admin.read` 下查看报价和库存流水，`offer.admin.manage` + 当前会话/action 绑定的一次性密码/TOTP reverify 才能冻结、解冻或永久下架。冻结禁止商家改价、上架或暂停；实物盘点仍可登记，不能改变冻结状态。解冻恢复 PAUSED，商家再显式上架，避免风险解除后自动恢复销售。DELISTED 不再接受库存调整或任何商家编辑。

报价修改和状态命令使用带引号 If-Match。报价 version 与库存余额 version 分开。`POST /merchant/offers/batch` 最多 50 个不同 Offer，只接受价格/履约 changes 和每项 expected_version；同一事务按稳定顺序锁定全部，任何错误全批回滚，不存在库存旁路。

## 库存调整

唯一商家库存写入是 `POST /merchant/offers/{id}/inventory-adjustments`：

```json
{"delta_qty": 10, "reason_code": "RESTOCK", "expected_version": 0}
```

delta 必须是非零有符号整数，原因 RESTOCK/COUNT_CORRECTION/DAMAGE。禁止 target_on_hand_qty、reserved_qty、operator。实物数量限制 0–1,000,000,000；可用数量由数据库生成 `on_hand-reserved`；约束 reserved>=0 且 reserved<=on_hand。调整锁定余额并核对版本，冲突返回 CONCURRENT_MODIFICATION；负调整侵占预占或余额超界返回 INVENTORY_ADJUSTMENT_CONFLICT。

库存幂等按商户/操作/key 唯一，包含 Offer、delta、原因、expected_version 的规范 payload 哈希。同商户不同员工重复同一个命令返回原结果；相同 key 改 payload 被拒绝。每次重放先复核当前 realm/RBAC/scope，撤销门店授权后不能用旧 key 绕过权限。流水记录调整前后实物、预占、版本及实际 actor，由触发器禁止 UPDATE/DELETE/TRUNCATE。流水、余额、审计与 Outbox 同 PostgreSQL 事务；中途失败全部回滚，同 key 可重试。

订单预占、支付扣减、释放与取消恢复尚属 M4，不能伪装成商家 Adjustment。本批通过真实 PostgreSQL 测试夹具建立已预占余额，验证负调整保护，不声称已经实现订单预占流程。

## 事件及搜索边界

报价变更发布 `OfferStateChanged`，库存调整发布 `InventoryAdjusted`；两者都是同事务事实引用。真实 RabbitMQ confirm 后进入持久 quorum 队列 `pawday.offer.facts`，M3.4 接入消费者前不消费、无 TTL。

现有搜索 `OfferChanged`/`InventoryAvailabilityChanged` 是带 sku_id/revision 的派生投影协议，不能直接把尚未构建投影的 Offer 引用送入该消费者。M3.4 消费事实、去重并由真实商品/Offer/库存建立投影，再发布上述搜索协议；本批不生成假价格、在售文档或假适配数据。搜索不可用不参与 Offer 事务。
